# I18N — English ↔ French, one deploy, no URL routing (Wave U)

The app is fully bilingual. French is **opt-in**: a toggle in the toolbar
next to the answer chip, stored in `localStorage` under `oeo_locale`,
default English. There is no `/fr/` URL prefix, no `Accept-Language`
sniffing, no RTL (French is LTR).

## How it works

| Piece | File | Role |
| --- | --- | --- |
| Core: locale store, `t()`, formatters | `src/i18n/index.ts` | module singleton + `useTranslation()` subscription |
| Provider | `src/i18n/I18nProvider.tsx` | mounted in `app/layout.tsx`, applies the stored locale after hydration |
| Toggle | `src/components/LocaleToggle.tsx` | toolbar button, keyboard-reachable, `aria-pressed`, Wave H a11y bar |
| Catalogs (generated) | `src/i18n/en.json`, `src/i18n/fr.json` | **do not edit by hand** — merged from `areas/` |
| Area sources (hand-edited) | `src/i18n/areas/<area>.json` | `{"en": {...}, "fr": {...}}`, one file per surface area |
| Merge | `node scripts/i18n-merge.mjs` | validates + writes the catalogs; `--check` fails if stale |
| Contract tests | `src/i18n/i18n.test.tsx` | key parity, no untranslated strings, fr-CA formats, toggle a11y |
| Coverage gate | `src/i18n/i18n-coverage.test.ts` + `scripts/i18n-coverage.mjs` | fails when a component hardcodes user-facing English or calls `t()` with a key en.json lacks |
| Runtime gate | `src/i18n/fr-runtime.test.tsx` | paints the four tabs in BOTH locale paths and fails when untranslated text reaches a French reader |
| Locale-deps gate | `src/i18n/locale-deps.test.ts` + `scripts/i18n-locale-deps.mjs` | fails a `useMemo` that caches text without `t`/`locale` in its deps |

### Adding a string (the workflow)

1. Pick a namespaced key: `area.thing` (`overview.efficiencyTitle`,
   `money.billWaterfallNote`). Dots, lowerCamel after the namespace.
2. Add it to your area's JSON under **both** `en` and `fr`.
3. Run `node scripts/i18n-merge.mjs`.
4. In the component: `const { t } = useTranslation(); … {t('overview.efficiencyTitle')}`.

`useTranslation()` returns `{ t, locale, setLocale }`. The returned `t` is
referentially stable per locale, so **every `useMemo`/`useCallback` whose
body produces text must list `t` in its dependency array** — otherwise a
language switch keeps stale prose. Components that only format numbers need
`useLocale()` instead.

### The coverage gate (what catches a new untranslated component)

Wave U's contract tests pin the two catalogs against each other, but they
could not notice a component **added afterwards** that prints hardcoded
English. The coverage gate closes that hole. It runs inside `npm run test`
— the same local battery as everything else — and fails on two things:

1. **Forward:** any user-facing string literal in `src/` that bypasses
   `t()`. The sweep reads the TypeScript AST, so it sees JSX text nodes,
   literal children expressions (`{cond ? 'Live' : 'Authorised'}`,
   `{x && 'text'}`, template literals), the accessible/text attributes
   (`aria-label`, `title`, `placeholder`, `alt`, …), and recharts
   `label={{ value: 'WINTER' }}` annotation objects.
2. **Reverse:** any literal `t('key')` call whose key `en.json` does not
   define. `t()` degrades to printing the raw key at the user, so a typo
   is itself an untranslated string.

Run it by hand for a readable report:

```
node scripts/i18n-coverage.mjs             # report; exit 1 on drift
node scripts/i18n-coverage.mjs --json      # machine-readable
node scripts/i18n-coverage.mjs --write-baseline
```

**The baseline is empty — keep it that way.** It started as 165 entries of
frozen Wave-U debt (183 raw hits across 22 files: the import page, the EV
card, the money views, the merge summary …) and every one of them has been
translated and `t()`d. `src/i18n/coverage-baseline.json` now holds
`{ "_readme": …, "entries": [] }`. The gate stays two-sided on purpose: a
string you *fix* but forget to delete from the list also fails, so the file
cannot silently drift back into a licence. Do not grow it for new work; add
the string to an area file and use `t()`.

The sweep does not flag canonical English data (`Off-Peak`, `TOU`, …), the
product name, a literal inside `<code>`/`<pre>`
(`dmd_export_b64.py --b64` — a command has no French spelling), or strings
built dynamically (`t(\`tab.${id}\`)`) — those are I18N.md's "deliberately
NOT translated" list, translated at the display layer by `planLabel()` /
`periodLabel()`, and not statically resolvable. The product name is a
`PROPER_NOUNS` set in `scripts/i18n-coverage.mjs`; it carries the same text
as `app.title`, which is what the places that DO translate render.

### The runtime gate (what the catalogs cannot prove)

The coverage gate is a SOURCE sweep: it proves nothing hardcoded escapes, and
nothing more. It cannot see the class qa measured on the deployed tip
7ee0375 — **strings that ARE in `en.json` rendering untranslated under
`lang="fr"`** — because every piece of that defect is locally correct:

1. **A stale `useMemo`.** Most prose here is produced inside pure lib
   functions that read the module locale at CALL time (`@/i18n`'s header
   explains why). A memo whose deps miss `t` therefore keeps the previous
   language: the toggle re-renders the chrome around it and the sentence
   underneath stays English. Fix: `t` (or `locale`) in the deps array — that
   is the whole change, no plumbing.
2. **A canonical constant printed where a label belongs** (`meta.label`
   instead of `t(meta.labelKey)`, `group.label` instead of `t(group.labelKey)`,
   the raw `DAY_LABELS` instead of `dayLabel()`).
3. **A sentence composed in a lib that never reached the catalog** — the
   literal is built by a template, so the coverage gate's forward sweep has no
   literal to point at.
4. **A raw key.** `t()` degrades to printing the key; a catalog that defines
   only the plural pair (`accrual.measuredLine_one`/`_other`) used to fall
   through to the key text when the caller passed no `count`. `t()` now falls
   back to `_other` — the countable default in both locales.

`src/i18n/fr-runtime.test.tsx` paints the real four-tab page over the
three-bill open-tail fixture and applies three rules, per TEXT NODE:

| Rule | Fails when |
| --- | --- |
| parity | a node's text equals an `en.json` value whose `fr.json` value differs — the catalog HAS French and the page is not showing it — **or**, since t_0a96fd14, equals that value's MASKED form (digits and `{placeholders}` → `#`), so a sentence the lib composed from an English template is named by the key it should have rendered instead of hiding behind its numbers |
| raw key | a node's text is a catalog key (`accrual.measuredLine`) |
| english | a word appears in the English catalog and NEVER in the French one (a composed sentence that never reached the catalog) |

It walks **both** user paths, because they fail differently: `cold` (the
stored locale is French before the first render) catches 2–4, and `flip`
(English first, then the toggle — the real `I18nProvider` ->
`restoreStoredLocale` path) catches 1. A third test pins SENSITIVITY: on the
same page in English the parity rule fires on 30+ nodes, so a clean French
sweep is not an empty sweep.

The same file also paints the **refusal notice**
(`SeriesNotesNotice`, t_12d39853) with the notes a real parse produces — the
fixture's own, plus one document per sibling sentence — because that row only
exists after an import commits, so the seeded dashboard sweep never reached it.
Its third test is the sensitivity half: the exact English sentence qa found on
the live fr page must still trip the `english` rule.

It also paints the **UsagePoint picker** (`UsagePointPicker`, t_203c6445) on a
document carrying two identified meters and one the feed never attributes to a
UsagePoint, because the heading is composed in the LIB (`lib/energy.ts`:
`UsagePoint <id>`, or `Meter` when no id) and the same fixture-shaped blind spot
applied: the picker only renders for 2+ groups, and then only after an upload is
pending, so nothing had ever painted it. A French reader read the English word
`Meter` — and, measured while adding the sweep, the **`english` rule cannot see
that word**: the fixture's own bill lines say "Current Meter Read", so `meter`
sits in the data vocabulary this gate exempts. The parity rule is what catches
it: `group.label` IS an `en.json` value whose `fr.json` value differs
(`gbseries.point.unidentified`), so a render site that goes back to
`group.label` repaints that value verbatim and fails. The sweep's third test
pins both halves.

It also paints the **multi-file merge review** (`MultiFileMerge`, t_dd0263c0) on
two files at once — a single-meter `file1.xml` plus a multi-group `dual.xml`.
That dialog composed its per-file summary line in a template literal
(`` `${f.name}: ${f.rows} kept, ${f.duplicates} duplicate` ``), which no gate
could see: a literal inside a `.map(…).join(…)` call is neither a JSX text node
nor a top-level collected expression, so it shipped English inside French chrome
and nothing flagged it. The line now reads through four catalog keys
(`merge.fileKept`, `merge.fileDuplicates` — each a `_one`/`_other` pair, because
`t()` keys the plural off exactly ONE `count` and the line carries two: the
`{rows}` agreement rides the first key, the duplicate clause is its own key).
The English pair is identical on purpose, so the en page keeps its wording byte
for byte (including `2 duplicate`, not `2 duplicates`); the French agrees on
both counts (`conservé`/`conservés`, `doublon`/`doublons`). The sweep's third
test is the sensitivity half — the exact English line must trip the `english`
rule — and the per-sweep identity is the two file names and the UsagePoint ids,
so `kept`/`duplicate` stay subject to the rules.

It also paints **"Your actual bill"** (`ActualBillPanel`, t_0a96fd14) — which is
the row the live instrument kept reporting, and the reason the panel's data
exemption changed. qa's sweep counted **3** English nodes on the fr page after
t_5e0926f1, all of them bill-line names read verbatim from the file (`Ontario
Electricity Rebate`, `Billing Period - Current Read Date`, `Billing Period -
Previous Read Date`). Those three were the visible tip of a wider class: the
sweeper matches a node against `en.json` phrases, so only names that happen to
contain one (`slice.credit.label`, `scope.billingPeriod`) were counted — the
class is the whole `<note>` vocabulary the committed bills carry: **21 names**
in the two synthetic electricity bills, **51** once the Enbridge Gas (Ontario)
feed (`utility-enbridge-gas.xml`) joined them as a SECOND provider's document.
The decision, consistent with `periodLabel()` for rate-period names, is that the
file's DATA stays canonical and the app owns the LABEL: `src/i18n/billNote.ts`
maps a normalised note onto a `billnote.*` key (`areas/billnote.json`, en + fr)
and the panel prints `billNoteText(item.note, t)`, keeping the utility's exact
wording on the node (`data-bill-note`, plus a `title` tooltip whenever it
differs) so the bill can still be checked line for line. Two properties make it
safe: the **English catalog values ARE the utility's wording byte for byte**
(the en page renders exactly as before — pinned against every committed
fixture), and a name no key covers prints verbatim with `t()` never called
(`billNote.test.tsx` plants an unknown name and a translator that throws). The
H.S.T. line, whose name carries the utility's registration number, travels as a
template (`H.S.T. # {n}` → `TVH n° {n}`). The panel's blurb states the rule in
both locales ("hover one for the utility's own wording").

Coverage only grows the way that ratchet allows: a provider's document is
committed as a fixture (provenance in `webapp/tests/fixtures/README.md`), every
name it states is added to `PROVIDER_BILL_NOTE_KEYS` with the file's own
wording as the `en` value plus a French view, and `billNote.test.tsx` pins the
two-way identity — no name without a key, no key without a name. The Enbridge
feed is what makes "unrecognized provider label" a measured class instead of a
claim: 37 lines, 7 of them worded exactly like Oakville's, the other 30 printed
English on the fr page before the catalog grew. A utility whose document is
never committed still prints its own wording (the documented fallback) — which
is correct, and still English, because the catalog may not invent a label no
document states.

The same catalog line names a SECOND surface: the plan-timeline detection strip
(`PlanTimelineEditor`, Plans tab) quotes the bill lines that produced its
verdict ("Evidence: On Peak-Summer · Mid Peak-Summer · Off Peak-Summer"), and it
paints them through `billNoteText` too, keeping the verbatim list on the node
(`data-bill-evidence` + tooltip). That row is worth knowing about as a GATE
lesson: it shipped English for a wave and neither the `english` rule (its words
— `peak`, `summer`, `mid`, `off` — are the fixture's own vocabulary, which the
rule exempts) nor the parity rule (the node is a JOIN, not a catalog value)
could see it. It became visible only when the names entered the catalog and the
live sweep's substring matcher found a phrase inside it — i.e. the instrument
found it, not the unit gate. A bill written under a plan whose line names this
catalog does not cover (`BLOCK 1 - Winter`, `Tier 2`, `Ultra-Low Overnight`)
still prints them verbatim, which is the documented fallback, not a defect.

The `english` rule needs an exemption list, and it is deliberately three
narrow things — **not** a baseline:

- words the French catalog itself uses (so French prose never trips it),
  **plus** the French month/weekday vocabulary the app's own `fmtDate`
  produces (`20 sept. 2026` is French although no catalog entry spells
  `sept`);
- canonical codes and units (`ULO`, `TOU`, `TIERED`, `kWh`, `$/kWh`, …);
- the utility's own vocabulary, read OUT OF THE FIXTURE at test time
  (`summary.items[].note` — `Bill Post Date`, `On Peak-Summer Usage`,
  `Distribution Loss Factor`, …) plus a node that IS one of those notes
  verbatim **while this app has no localized view of it**. That exemption is
  narrow on purpose: since t_0a96fd14 every name the shipped fixtures carry IS
  translated (see below), so `billNoteKey(text) === null` — not "it is a note
  the file carries" — is what excuses a node. A row the panel forgets to
  translate therefore fails the parity rule instead of riding the exemption;
- and, per sweep, the file's own **identity**, read out of the documents that
  sweep paints at test time: the refusal notice's series identity
  (`up-B · mr-B1 · Wh (uom 72)`), and the picker's own UsagePoint ids plus the
  name the user's file carries (`oakville-export.xml` — the picker prints it
  verbatim, the same class as a bill line). A meter id, a ReadingType id, the
  id inside a heading and the unit the file declared are the file's data — the
  sentence AROUND them is chrome, so this vocabulary is passed in per sweep
  (`sweep(root, extraVocab)`) and never added to the global sets: that is
  exactly what keeps `Meter` (chrome) subject to the rules. The ESPI unit
  symbols and multiplier names the parser prints inside those sentences come
  from the module that prints them (`UnitSymbolKind` / `UnitMultiplierKind` in
  `lib/greenbutton/espiUnits.ts`), plus the `uom` field name, so that half
  cannot drift either.

`src/i18n/locale-deps.test.ts` (scanner: `scripts/i18n-locale-deps.mjs`) is the
authoring-time twin of rule 1: it walks `src/` with the TypeScript compiler,
resolves the import graph, and fails any `useMemo` that produces
locale-dependent output (a `t()` call, an `@/i18n` formatter, or a call to a
function that does either) without `t`/`locale` in its deps. `useCallback` is
exempt on purpose: its body runs when the event fires, so it reads the
CURRENT locale. Both gates carry planted-failure probes, so a scanner that
stopped working cannot pass by reporting nothing:

```
node scripts/i18n-locale-deps.mjs          # report; exit 1 on drift
node scripts/i18n-locale-deps.mjs --json
```

Adding a string is still the same one workflow (area file → `i18n-merge.mjs`
→ `t()`); what the two new gates add is that the RENDER SITE can no longer
keep the old language, and neither can a canonical constant stand in for a
label.

### Interpolation and plurals

- `t('reset.body', { count: 3 })` picks `reset.body_one` / `reset.body_other`
  via `Intl.PluralRules` when those keys exist (French `0` and `1` are both
  singular — that is `Intl`'s rule, not ours).
- Placeholders are `{name}`; both locales must use the same placeholder set
  (the contract test enforces it).

### Numbers, money, dates

Never hand-write `$1,365.03` or `Aug 26`. Use the formatters in `@/i18n`:

| Formatter | en-CA | fr-CA |
| --- | --- | --- |
| `fmtMoney(1365.03)` | `$1,365.03` | `1 365,03 $` |
| `fmtMoney0(812)` | `$812` | `812 $` |
| `fmtSignedMoney(-45.1)` | `−$45.10` | `−45,10 $` |
| `fmtCents(0.4)` | `0.4¢` | `0,4 ¢` |
| `fmtKwh(8.7)` | `8.7 kWh` | `8,7 kWh` |
| `fmtPercent(63)` | `63%` | `63 %` |
| `fmtNumberAuto(1.0376)` | `1.0376` | `1,0376` |
| `fmtDay('2025-08-26')` | `Aug 26` | `26 août` |
| `fmtDayRange(a, b)` | `Aug 26 – Sep 24` | `26 août – 24 sept` |

`fmtDate(d, pattern)` is `date-fns/format` bound to the active locale, so
chart axis ticks and table cells use French month/weekday names.

### The money-format contract (why a green battery was not enough)

Wave U shipped the formatters above and a French money fix; the fr-CA build
still printed `1 420,89 $$/AN` on all four plan-cost headlines, `kWh kWh`
three times on Plans, and `11.9¢` beside `3,9 ¢` on one page. The formatters
were correct — the RENDER SITES were not. Two rules now hold, and
`scripts/money-contract.mjs` + `src/i18n/money-contract.test.ts` fail the local
battery when either is broken:

1. **A number a person reads is formatted by `@/i18n`.** No `$${n.toFixed(2)}`,
   no `toFixed(1)}¢`, no `toLocaleString('en-CA', …)`. `toFixed` always emits a
   `.` decimal separator, so any raw one is the `11.9¢` beside `3,9 ¢` class.
   `data-*` attributes are exempt (machine-readable test hooks).

       node scripts/money-contract.mjs           # report; exit 1 on drift
       node scripts/money-contract.mjs --list    # every pinned render site

2. **A catalog template that prints a unit takes a BARE number.** `{kwh} kWh`
   wants `fmtNumber(kwh, 1)`; handing it `fmtKwh(kwh)` prints `kWh kWh`. Same
   for `{cents}¢` (`fmtNumber`, not `fmtCents`) and `{rebate}¢`.

A money unit that rides NEXT TO money is symbol-free by definition:
`moneyPeriodUnit('yr')` is `/yr` · `/an`, never the `$/yr` · `$/an` toggle
label — appending that to `fmtMoney`'s output is exactly the `$$/AN`
regression. And a translated sentence puts the dollar sign where ITS locale
puts it: fr-CA writes `0,0252 $/kWh`, so the French catalog may not keep the
English `${perKwh}` order (`charge.detail` did).

The rendered half is pinned by `src/components/MoneyLocale.test.tsx`, which
walks all four tabs in BOTH locales over the three-bill open-tail fixture and
counts painted text nodes for a doubled symbol, a French `$` before its
number, a doubled unit and the wrong decimal separator. `evidence/money-locale-verify.cjs`
is the same sweep against a running build (local or deployed), with screenshots.

## What is deliberately NOT translated (canonical data)

Per the Wave U spec, the app's data layer stays English — the files
themselves are English, and fingerprints must keep matching them:

- **Plan ids** (`TOU` / `Tiered` / `ULO`) in storage, `data-*` attributes,
  URL hashes, classifier fingerprints.
- **Rate-period names as data** (`Off-Peak`, `Weekend Off-Peak`, `BLOCK 1 -
  Winter`, `Tier 2`): these are the utility's own line names. The classifier
  (`lib/planTimeline.ts`, `lib/moneyViz.ts`) matches them with regexes that
  now also accept the **French wording an Oakville bilingual export would
  emit** (`Période creuse`, `Période de pointe`, `BLOC 1`, `Palier 1`, …).
  Oakville Hydro's actual DMD feed emits English only (verified against
  Mark's own export); the French anchors are there so a bilingual CSV/XML
  export classifies honestly instead of silently reading as `unknown`.
- **Bill line names as data** (`BillLineItem.note` — `Total Electricity
  Charges`, `Billing Period - Current Read Date`, …): classification, grouping
  and every completeness check read the raw note, and the raw note is what the
  panel keeps on the node (`data-bill-note`). `billNoteText(note, t)` is the
  *localized view* of them — the same shape as `periodLabel` for rate-period
  names — and it falls back to the raw note for any name the catalog does not
  cover.
- **Raw XML / JSON payloads.**
- **The product name** "Ontario Energy Optimizer" (proper noun).

`planLabel(plan)`, `periodLabel(name)` and `billNoteText(note, t)` give the
*localized view* of canonical names for display; `PLAN_LABEL`, the raw period
strings and `BillLineItem.note` stay canonical.

## CMD agreements and bilingualism (the regulatory check)

Wave U asked whether Ontario utilities already provide Connect My Data
(CMD) agreements bilingually. **Finding: no such rule exists.** The OEB's
Green Button framework (ERO notice 013-1874, province-wide DMD/CMD
implementation) contains no French-language requirement for authorization
agreements; the French Language Services Act binds Ontario government
services, not electricity distributors' customer agreements. Utilities
serve French-speaking customers through voluntary channels, not a CMD
bilingualism obligation. So there is nothing to "match" — our own connect
flow is translated because the toggle demands full coverage, not because a
regulation requires it.

## Known gaps (the honest list)

Strings flagged NOT-YET-TRANSLATED during the Wave U review live here.
Add to this list instead of shipping a silent half-English surface.

Verified by a source sweep over every non-test `.ts`/`.tsx` outside
`src/i18n/` (a regex for string literals that look like English prose).
What it still finds, and why each is deliberate:

**Server-rendered or never reaches the toggle**

- `metadata` in `app/layout.tsx` (browser-tab title, PWA manifest
  strings): server-rendered, so it follows the request, not the toggle.
  Stays English in both modes — a real gap if the installed PWA title ever
  needs French.
- `public/manifest.webmanifest` + service-worker strings: same reason.
- `app/greenbutton/notify/[token]/route.ts` — the literal `Not Found`
  HTTP response body, not app chrome.
- `lib/greenbutton/config.ts` — a server-side startup warning logged to
  the operator, never rendered.
- `lib/greenbutton/oauth.ts` — the `Basic ${base64}` Authorization header
  prefix (not prose).

**Canonical English kept on purpose, translated at the display layer**

These are data the code, tests, or classifier key off. Each carries a
`_KEY` / `key` companion the render layer passes to `t()`:

- `lib/tabs.ts` — `TABS[].label`/`title`/`description`; `TabNav` renders
  `t('tab.' + id)` / `t('tab.desc.' + id)`.
- `lib/moneyViz.ts` — `ESTIMATE_KEY_LABEL`, `DELTA_LABELS`,

- `components/MoneyStackedChart.tsx` — `KIND_BADGE[].text`

- `lib/exampleData.ts` — `EXAMPLE_DATA_LABEL` (asserted by its own test;

- `lib/energy.ts` — `BASELINE_ESTIMATE_CAPTION` (same: test-only).

  knowing: `Meter` is the one lib-composed word the runtime gate's vocabulary

  regression catchable at all.

**Not prose**

- `ERR-…` incident ids, file names, `yyyy-MM-dd` storage values.
- `lib/storage.ts` / `lib/backup.ts` structural guards whose message IS
  the schema (`{ timestamp: number, usage_kwh: number }`) — translated
  around the shape, which stays literal.
- Utility names in the selector (proper nouns).

**Chart tooltips** driven by `recharts` `labelFormatter` closures
pre-computed outside React: where found, they read `t` at render (the
Wave U review found and fixed every current instance).

### The canonical-plus-key pattern, in one paragraph

Where a value is both *data* (tests assert it, regexes match it) and
*shown to a person*, the code keeps the English constant and exports a
companion key the display layer translates. That is why the sweep above
still lists `lib/tabs.ts` and friends: they are not untranslated surfaces,
they are the untranslated *source* of translated surfaces.
