| 2026-10-12 (i18n, merge summary line) | The multi-file merge review's per-file summary line — `file1.xml: 5 kept · file2.xml: 5 kept, 2 duplicate` — is **composed in the catalog, not in a template literal**. It was invisible to every gate: a JSX expression child at the top level is collected only when the expression itself is a literal/ternary/`&&`, so a literal inside `.map(…).join(…)` was never scanned, and `MultiFileMerge` renders on no sweep (the dashboard fixture is one file). It now reads through **two keys**, each a `_one`/`_other` pair: `merge.fileKept` (`{name}: {rows} kept` / `{name} : {rows} conservé(s)`) carries the `{rows}` agreement, and `merge.fileDuplicates` (`, {duplicates} duplicate` / `, {duplicates} doublon(s)`) is the duplicate clause on its own — `t()` keys the plural off exactly ONE `count`, and this line carries two, so one count had to travel as a plain param. The English pair is **identical on purpose** (`_one` = `_other` = `kept`/`duplicate`), so the en page keeps its wording byte for byte — including the existing quirk `2 duplicate` (not `2 duplicates`), which the component test pinned before and still pins; the French agrees on both counts. `MultiFileMerge.test.tsx` pins both locales (incl. the singular `1 conservé, 1 doublon` and the flip), and `fr-runtime.test.tsx` **paints the dialog** — two files at once, a single-meter `file1.xml` plus a multi-group `dual.xml` whose chosen group repeats a timestamp — sweeping cold + flip, with the sensitivity half on the exact English line and a per-sweep identity of the two file names + UsagePoint ids | Same defect class as the picker heading and the refusal notice, one surface over: English composed in code and painted on the French page. The literal was undetectable *by construction* (the coverage scanner does not descend into a call's argument), and no sweep mounted the dialog, so nothing had ever flagged it — the only reason it survived the wave that fixed its siblings. Two keys, not one, because a single catalog key can carry only one plural discriminator and the line counts two things independently (`5 kept, 2 duplicate` has to agree on `rows` and on `duplicates`); keeping the English `_one`/`_other` identical keeps the en page minted from the same catalog without changing a byte. The counts are not lib-composed (the component owns them from `mergeReadings`), so unlike `SeriesNote`/`UsagePointGroup.label` there is no canonical English constant to preserve with a key companion — the catalog IS the source, which is why no new display-layer module was needed | A single `merge.fileLine` key with a nested clause (still two `t()` calls under the hood, and it hides the two-count problem instead of stating it); pluralising the English too (`2 duplicates`), which changes the en page for a pure i18n fix and contradicts the byte-identical rule the sibling cards held; a display-layer module (there is no lib string to keep as the English source — over-engineering for a component that already owns the values); leaving the literal and widening the coverage scanner to descend into call arguments (a scanner change with repo-wide blast radius, for one line) |
