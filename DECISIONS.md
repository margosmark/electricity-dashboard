# Decision log — why the electricity dashboard is built this way

Short, dated, in newest-first order. Each entry: the decision, why, and what
was rejected.

| Date | Decision | Why | Rejected |
| --- | --- | --- | --- |
| 2026-10-04 (webapp always-on floor) | The webapp's base load is **interval-aware**: `energy.ts` gains `inferIntervalHours()` (modal gap between consecutive epoch-SECONDS `timestamp`s, ties → shortest) and `calculateVampire` / `calculateAlwaysOnFloor` divide the per-interval P05 by it *before* any `×24 h/day` extrapolation; `bottomFivePercentKwh` is renamed `bottomFivePercentKwhPerInterval` so the unit is in the name. `buildHeatmapData` divides a cell's sum by distinct **days**, not readings | `usage_kwh` is energy per reading interval, and Green Button / ESPI feeds are commonly 15- or 30-minute — `P05 × 24` priced a quarter-hour as a full hour, so on a 15-minute export the watts, kWh/day, $/yr and the heatmap tooltip all came out exactly 4× low, silently, because every bundled fixture is hourly (pre-fix `app.py` on a synthetic 15-min house: 0.179 kWh where the hour holds 0.717); hourly feeds divide by exactly 1.0, so no existing number moves | An hourly-only contract (reject non-hourly exports — punishes a valid file and keeps the unit lie in the helper); converting only the label while leaving `kwhPerDay = base * 24`; touching `floorCost` / `billShare` (they sum over rows and are already cadence-independent) |
| 2026-10-04 (Streamlit chart labels) | The frozen prototype's two per-interval means group by `('date', 'hour')` **first**: Daily Routine sums an hour's readings then averages those hour totals, "Avg Vacation Hourly Usage" does the same over the days selected | Both charts labelled per-interval energy as hourly — 4× low on a 15-minute export, unchanged (bit-identical) on the hourly demo; group-by-then-average is the smallest edit that makes the label true | Re-labelling the axis to "Avg kWh per reading" (admits the unit is wrong instead of fixing it); rewiring the charts (the prototype is frozen) |
| 2026-10-04 (Streamlit vampire) | Vampire $/mo is **interval-aware**: `vampire.py` measures the reading interval from the modal gap between consecutive `datetime` values and divides the P05 by it, so `estimate_base_load_kw()` returns a real kW on 15- and 30-minute exports too; the metric help names the interval it detected | Green Button / ESPI feeds are commonly 15- or 30-minute IntervalReadings — `kWh-per-reading × 24` priced a quarter-hour as a full hour and understated the figure exactly 4× ($2.86 vs $11.43 for the same synthetic house); hourly feeds divide by exactly 1.0, so no existing number moves | An hourly-only contract (reject/warn on non-hourly data — punishes a valid export and keeps the unit lie inside the helper); renaming to `base_load_kwh_per_interval` and dropping the kW claim (fixes the name, not the money) |
| 2026-10-02 (Wave E) | Block **classification** ships two signatures only — `classifyBlock`: fixed-schedule (≥3h, flat across hours, steady week to week, same slot ≥4/5 weeks) → "HVAC-like" broad daytime span that fails either steadiness test → otherwise **"Unidentified weekday routine"** | The real file can't support more: the 3 named labels land on 3 HVAC / 3 fixed / 11 unidentified blocks, and naming an appliance we can't see is worse than saying we couldn't | A third/fourth guessed signature ("water heater", "EV charging" as fact), an ML clustering pass, or labelling every block |
| 2026-10-02 (Wave E) | **Headline collapse** when one destination owns >50% of `bestMonthlySavings`: one sentence ("Switch to ULO and move your weekday routine → ~$84.76/mo") + blocks demoted to supporting rows; headline wears the WORST confidence badge of the rows | On the real file all 17 blocks recommended the same move — 17 identical conclusions is noise, not evidence | Keeping one full card per block (the verified Wave D behaviour); collapsing at ≥50% (a tie is not a consensus); hiding the per-block evidence |
| 2026-10-02 (Wave E) | **Mid-Peak ships as a lower tier**: TOU Mid-Peak hours join the analysis behind the On-Peak blocks, baseline = `tou.midPeak` for TOU and the user's OWN plan rate otherwise | Shifting Mid-Peak→off-peak is real money the optimizer was silently leaving out ($40.17/mo of the real file's $84.76) | Pricing every plan at `tou.midPeak` (a ULO user doesn't pay it → fabricated savings); keeping On-Peak only |
| 2026-10-02 (Wave E) | **Effort chips** (`no plan switch` / `plan switch required`) derived from the selected plan, and the assumption text made plan-aware to match | A Tiered household was being told "no plan switch" for a TOU-only window — the chip and the sentence must never disagree | Hard-coded assumption strings (Wave D) with a plan-agnostic chip; chips that only restate the existing text |
| 2026-10-02 (Wave D) | ToU-shift optimizer is a **pure** `analyzeTouShifts()` (`lib/touShift.ts`) over On-Peak cells: recurring = same weekday+hour block present in ≥3 of the last 5 data-anchored weeks with CV ≤ 0.4 and ≥0.05 kWh/wk; ranked per-block savings vs ULO-overnight / weekend / off-peak-TOU rates, rendered as `ShiftOptimizer` cards in Insights | Replaces the Streamlit-era "% shift" slider with concrete dollar-ranked moves; window anchors to the newest reading (never `Date.now()`) so it's deterministic and unit-testable; empty states are honest (`no-recurring-onpeak` / `insufficient-history` + week counts) instead of a fake 0 | A generic % slider (no actionable target); anchoring to today (non-deterministic, breaks on stale files); requiring a plan switch without labelling it (assumption printed per option instead) |
| 2026-10-02 (Wave D) | PWA via plain `public/sw.js` + `manifest.webmanifest` (shell + `/api/rates` caches, network-first API with cache fallback, prod-only registration) — no next-pwa plugin | Works with no connection (all math is client-side; localStorage holds readings); zero new dependencies; `sw.js` served with `Cache-Control: no-cache` so a deploy isn't trapped behind a stale SW | next-pwa/workbox plugin (build complexity, version-pinned to Next); caching `/api/rates` cache-first (would serve stale rates after an OEB update) |
| 2026-10-02 (Wave D) | E2E smoke boots the **real Docker image** in CI: HTTP assertions (`tests/e2e/http_smoke.sh`) + Playwright (`tests/e2e/smoke.spec.ts`) driving upload of a synthetic 68-reading GreenButton XML, Shift-Optimizer blocks, SW/offline, and Chrome's `Page.getInstallabilityErrors` audit | Gates the artifact users actually run (fresh container, prod build), not `next dev`; fixture is synthetic (committed under a scoped `.gitignore` negation — the root `*.xml` privacy rule silently dropped it from the first CI run); whole job runs in ~76s | Testing only against `next dev` (misses standalone/prod-only paths like SW registration); real meter XML in the repo (privacy rule exists for a reason); Playwright browser download in CI (uses runner's Chrome, `channel: chrome`) |
| 2026-10-02 (Wave B) | True-bill add-ons (delivery $/kWh *and* $/month, regulatory $/kWh, HST %) are **local user inputs**, seeded empty in `localStorage.extra_charges`; all empty ⇒ estimate and caption stay exactly as before | `/api/rates` is commodity-only — delivery/regulatory/HST are utility-specific and not ours to invent; an empty field must not change the existing figure | Deriving add-ons from the OEB rate sets; seeding HST at 13% (that would silently change every existing estimate) |
| 2026-10-02 (Wave B) | Readings are grouped per UsagePoint (id taken from each entry's `UsagePoint/<id>` link) and a picker asks which meter to load; `parseGreenButtonXML` keeps its merged semantics as the one-meter fallback | Green Button exports can carry several meters/rate classes — merging them corrupts every kWh and cost figure with no visible error | Keeping the merged parse as the primary path |
| 2026-10-02 (Wave A) | First-load window picked by `selectInitialWindow`: anchor `min(last data day, today)`, then accept the first of billing period → calendar month → trailing data-anchored window whose days are at least half covered by readings | Anchoring the billing period on the last data day opened Oct 1–31 for a feed ending Oct 1 (~12h of data in a 31-day window) — a fresh upload looked empty | Clamping the window end to the data (leaves a 1-day window); falling back to Month alone (with `billing_day=1` the Month window *is* the empty billing window) |
| 2026-10-02 (Wave A) | Totals strip (`calculateFullDataTotals`) sums **every** reading, reusing the chart's monthly buckets | Answers "what would all my data have cost on each plan, and what is the gap between best and worst" — the plan-decision number, independent of the visible window | Summing per-interval `costTiered` (flat tier-1 only, understates Tiered); totals over the visible window (duplicates the plan cards) |
| 2026-10-02 (Wave A) | Tab markup split into `ChartView.tsx` / `InsightsView.tsx`, state stays in `hooks/useDashboard.ts` | Dashboard.tsx mixed nav, two tabs and modals in a 300-line file; each tab is an independent feature surface | Routing per tab (it is a single-screen tool) |
| 2026 (CI wave, #2) | Two-job CI: webapp (lint/typecheck/vitest/build) + Python (pytest for `parser.py`) | The repo carries both the legacy Streamlit parser and the live webapp; each layer is gated by the tests that own it | Single combined job (slower, mixes toolchains) |
| Mid-2026 | Weekend bars in the daily view get orange-highlighted by `getBarColor` (PR #1, `feature/weekend-bar-colors`) | Weekend consumption patterns differ; color makes weekly rhythm visible at a glance | Separate toggle/legend — visual, zero UI cost |
| Mid-2026 (be3fdf6) | Comprehensive test suite + `husky` pre-commit hook | Money-adjacent math (rate comparisons drive real spend decisions); regressions in `classifyTOU`/tier proration would be silent otherwise | Manual verification only |
| Mid-2026 (d57c49c) | Bumped Next.js to 16.3.0 purely for security advisories | Self-hosted container with `restart: always` running unattended; patch level matters more than feature parity | Staying on the older major |
| Mid-2026 (fd1465c) | `.worktrees/` ignored for kanban worktree-per-task isolation | Bot tasks on this board run in git worktrees; worktree dirs must never be committed | Per-task clones (heavier) |
| Design-time | Next.js webapp replaces the Streamlit prototype; Streamlit kept but frozen | Streamlit can't do client-side file parsing + persistent local state in a deployable single container; Next.js standalone works in compose with no backend | Rewriting Streamlit further; adding a DB |
| Design-time | **No server-side data storage at all** — uploads parse in-browser, cache to `localStorage` | Privacy: hydro consumption data never leaves the machine; zero server state to secure or back up | Upload endpoint + Postgres (a finance-grade backend is wrong for one-user notes) |
| Design-time | Rate history as versioned `RateSet`s in `/api/rates`, matched per reading date | Ontario rates change annually (e.g. ULO on-peak 24→28.6→39.1¢/kWh across the three sets); per-date matching makes historical cost math reproducible instead of rewritten on each update | One current rate constant (wrong retroactively) |
| Design-time | Compute all three plans (TOU, Tiered, ULO) per interval regardless of selected plan | The product's whole point is *comparison*; a readings-time single-plan pipeline would need a recompute per plan switch | Computing only the selected plan |
| Design-time | Tier thresholds prorated `(days/30.4)` per aggregation bucket | OEB tiered thresholds are monthly allowances;Two-tier math must respect bucket length or short months overcharge tier2 | Fixed monthly threshold on any bucket |
| Design-time | "Vampire" base load = 5th-percentile hourly draw, not the minimum | A single minimum hour is noise (one sensor hiccup); the 5th percentile is a stable "always-on" estimate | min() as in the Streamlit prototype |
| Design-time | All analytics as pure functions in `lib/energy.ts`; `Dashboard.tsx` only state/markup | Testability without rendering; the dashboard stays a thin shell | Mixing math into components |
| Design-time | Neobrutalist UI language (thick borders, hard shadows, yellow highlights) | Deliberate visual identity (the repo predates it: `b4ae405` era); no design-system dependency to maintain | shadcn/Tailwind default look |
